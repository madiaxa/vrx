# Known limitations and verification boundaries

- **Physical display timing:** no portable Iced 0.14 API reports per-word scanout timestamps. Diagnostics distinguish nominal deadlines, timer wake, UI dispatch, and renderer command submission. None is proof of physical presentation. 4,000 WPM requests a 15 ms interval, faster than a 60 Hz frame; words may never reach scanout even when the engine skips zero tokens. VRX does not claim real-time scheduling or sub-millisecond OS wake precision.
- **Unicode segmentation:** tokens are delimited by whitespace-based graphemes and after slash-based graphemes (the slash is retained); combining marks attached to a whitespace base are normalized away together with that separator. CJK without spaces and Thai/Khmer text need dictionary segmentation for useful individual-word RSVP. Bidi/contextual scripts fall back to whole-word focus. This is useful display, not validated per-grapheme ORP for those scripts. Combining marks and emoji remain intact. Attached punctuation counts in ORP length. NFC normalization is intentionally not applied; original graphemes are preserved.
- **Typography:** glyph bounds, not rasterized ink bounds, define the focal center. Ligatures can share a shaped cluster, so a ligature's visible highlight can cover more than one logical grapheme. Font availability and fallback vary by OS. Five family choices are exposed; arbitrary font-file loading and a system font picker are future work. A bundled OFL Clockette Mono font renders numeric controls, including Pitman digits. Fractional sliders use 1/radix steps, stored as the nearest thousandth for timing; typed values keep the existing precision. Compact spellings round-trip stored units but are not arbitrary-precision rational arithmetic. Focal guide shapes are desktop-only; ASS/MP4 carries the configured focal color. Very long words show a 256-grapheme excerpt around the focal point, scale down, and may become too small to read comfortably. Text is clipped to its reading area.
- **Accessibility:** labeled native Iced controls, large type, high contrast, color-independent guides, and reader keyboard shortcuts are implemented. Full platform screen-reader/AccessKit integration and complete Tab focus behavior are not implemented in this release. No animations are required for reading. Test with each intended assistive technology before relying on it.
- **Input:** only valid UTF-8 text and Markdown are supported. Binary/invalid UTF-8 input returns an error. Plain UTF-8 BOMs are accepted. No EPUB, PDF, HTML import, encoding guessing, hyphenation repair, or OCR. Markdown raw HTML blocks are omitted. Code blocks remain readable text. Sentence detection is heuristic, so abbreviations/decimals can produce false boundaries. A final closing punctuation grapheme is never split.
- **Text editing:** the in-window editor accepts current buffers up to 16 MiB; larger documents remain readable through import. It edits the readable document source, so imported Markdown has already had markup removed. Apply starts changed text at token zero, paused, as an unnamed session. It does not save edits to the original file or retain them across restart. Use export to retain a timed-text copy. Opening and editor-buffer construction run off the UI thread; collecting the edited text on Apply requires a temporary string. Native text-editing behavior on Linux/Windows/FreeBSD remains unverified.
- **Large documents:** limit 512 MiB source; millions of short tokens require substantially more memory for indexes. There is no streaming/chunked/memory-mapped importer. Background preprocessing and bounded requests preserve UI responsiveness, but disk reads, UTF-8 conversion, Markdown parsing, and fingerprinting are not fully interruptible. Cancellation is cooperative during token indexing. Reindexing an ORP strategy temporarily copies the source in a background job. No large-document measurement implies unlimited-memory support.
- **Persistence:** only files can be recovered; clipboard/demo content is not stored. Recent file paths disclose filenames in local settings. Fingerprints are stable 64-bit FNV-1a identity hints, not cryptographic authentication. Abnormal termination can lose up to 30 seconds of progress. Cross-process configuration writes are last-writer-wins. Atomic rename and fsync durability ultimately depend on the filesystem.
- **Export:** ASS and MP4 use an independent opaque export canvas (default chroma green), whole-word centering and ORP color; exported positioning is not identical to desktop per-grapheme anchoring. SRT has no styling and cannot carry a background. ASS timestamps are rounded to centiseconds; SRT to milliseconds; 60 fps MP4 is frame-quantized. ASS replaces literal braces/backslashes with fullwidth equivalents so input cannot become subtitle override syntax. Exports require sufficient disk space and can be long-running for a book. Cancel is available in the GUI. MP4 requires external FFmpeg with libass/libx264. Font substitution may differ in libass; editor import support varies. The temporary FFmpeg used for verification is not bundled or installed system-wide.
- **Platform status:** Apple Silicon macOS is the development target actually built and launched. Linux, Windows and FreeBSD configuration is implemented and CI/release workflows are supplied. A previous revision passed the complete FreeBSD target type-check; the latest update ran only three focused tests on macOS and was not cross-checked, but no remote CI, FreeBSD linking, cross-platform GUI, or assistive-technology results are claimed. Intel macOS, multi-monitor mixed DPI, display hotplug, and long soak/leak tests remain unverified. WGPU/Metal's transitive `block 0.1.6` currently triggers a Rust future-incompatibility warning.
- **Failure guarantees:** VRX's source forbids unsafe Rust and explicit panic/unwrap/expect paths, uses checked text access, clamps inputs, and reports recoverable failures. Allocator exhaustion, process signals, graphics drivers, OS/library failures, and third-party panics cannot be made impossible. No zero-crash or zero-leak certification is claimed.

These boundaries are release scope, not hidden completed features. Acceptance evidence and outstanding manual checks are listed in PERFORMANCE.md and RELEASE.md.
